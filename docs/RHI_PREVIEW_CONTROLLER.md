# CPU 预览入口与控制器

主编辑器现已另有 **Renderer** 菜单，可在实际编辑视口使用 DX11／DX12／Vulkan。
其实时数据、资源切换与兼容回退范围见 [编辑器 RHI 视口](RHI_EDITOR_VIEWPORT.md)。
本文以下内容描述独立的旧 **Renderer Preview** 窗口。

另有在旧编辑器初始化之前分流的可选启动入口，支持 CPU-only PMD/PMX
模型材质导入；它与本文的主编辑器菜单预览范围不同。使用及验收见
[无 DX9 设备的启动与模型导入](RHI_DX9_INDEPENDENT_STARTUP.md)。

## 职责

沿用 Unity 调研确定的职责边界，保留项目自己的接口和实现：

| 层 | 职责 | 不持有 |
| --- | --- | --- |
| CPU 场景生产器 | 场景遍历、最终求解姿态的 CPU 蒙皮、材质、纹理版本、完整帧 | RHI GPU handle |
| 后端工厂 `CreateBackendDevice` | 根据后端和驱动配置创建设备、交换链；返回创建失败原因 | 编辑器窗口与场景 |
| `ScenePreviewController` | 停止提交、缩放、暂停、设备替换、卸载、关闭 | Win32 类型、DX9 捕获对象 |
| Windows 预览宿主 | 菜单、窗口生命周期、客户区尺寸、状态提示 | 后端专用设备类 |
| `SceneRenderer` | CPU 版本缓存、上传、提交、完成后释放、设备重新绑定 | 窗口逻辑 |
| DX11/DX12 | 原生目标、着色器、资源、命令执行与完成同步 | PMM 编辑状态 |

接口分别位于 `rhi_backend.hpp`、`rhi_scene_preview.hpp` 和 `scene_preview_ui.hpp`。共用工厂和控制器也参与无界面资源构建；没有编译进来的后端明确返回 `backend_not_built`。

## 应用入口

`MIKUDANCESTUDIO_RHI_PREVIEW=ON` 编译菜单入口，运行时默认关闭。它独立于 `MIKUDANCESTUDIO_DIAG`；诊断关闭的产品构建也可使用 **Renderer Preview → Direct3D 11 / Direct3D 12 / Close previews**。选择一个后端会关闭另一个，关闭预览窗口会更新菜单并实际释放资源，主窗口仍使用 DX9。`F5` 重建设备；后端配置和数学策略在替换时保留。

支持范围是单采样、PMD、无 MME 的完整 CPU 场景。动态屏幕纹理、PMX、背景图片/AVI、自阴影合成等未支持操作阻断整帧，并在预览窗口显示原因。空的编辑器尚无 `SceneSession`，提示加载 PMM。有效场景恢复后，宿主显式 `Resume`，不会通过一次 `Resize` 意外解除阻断。

MME 的支持判断读取实际的 `Enable Effect` CPU 策略；桥接器已经初始化不表示效果已启用。预览不替用户改变这个开关，可使用现有 `Ctrl+Shift+E` 切换效果。动态屏幕纹理被阻断时，单采样验收选择原有 BackgroundRefresh 来源且不加载背景，表示空屏幕纹理。

## 普通帧与验收

普通帧直接消费 CPU 完整命令流。CPU 几何发布不读取或比较旧 GPU 顶点；资源来源是模型记录、独立系统内存饰品导入和解码后的纹理字节。`scene_cpu_submission.cpp` 在正式构建中只观察提交顺序，传入的 DX9 指针不被解引用。CPU 帧组装器和控制器都不接受 DX9 对象或捕获流。

产品默认使用可移植 BoxLinear Mip 准备；此结果不承诺与 DX9 D3DX 的 Mip 字节相等。严格原生图像验收显式选择独立 DX9 兼容准备器：它从 CPU 文件字节创建私有准备资源，缓存结果，没有读取应用已绑定纹理。此冷准备边界与逐帧绘制分开，不应将其描述为已完全移除 DirectX 的素材导入流程。

`MDS_RHI_*` 捕获与字段比较属于可选诊断。`--inputs direct` 要求匹配当前应用、GUI、素材及配置哈希的已通过审计；普通帧的几何记录必须全为 `cpu_source`，`cpu_inputs.*.csv` 必须缺席。有限的九个原生检查点继续提供逐字段和逐绘制图像证据，不能代替普通帧的来源检查。

## 生命周期

1. 客户区为零或最小化：暂停提交，不执行零尺寸 `ResizeBuffers`。提交期间发生最小化也返回暂停状态。
2. 有效缩放：交换链解绑并重建目标，epoch 递增，旧准备帧必须拒绝，纹理上传数量保持不变。
3. 设备替换：停止提交 → `SceneRenderer::Detach` 排空旧工作 → `Swapchain::Retire` → 释放设备 → 工厂创建新设备 → `Rebind` → 从 CPU 版本上传。旧设备身份的提交必须拒绝。
4. 场景卸载：释放 scene namespace 与缓存。未产生首帧的窗口也可卸载和关闭，重复卸载和关闭是有效操作。
5. 关闭：卸载、排空并释放渲染器，再释放交换链与设备，最后销毁宿主窗口。失败保持停止提交，允许 F5 或重新打开恢复。

## 验收入口

- `rhi_preview_dx11/dx12_warp/hardware`：x64/x86 各四个 CTest，覆盖三轮创建关闭、未绘制即卸载、连续缩放、零尺寸、最小化、替换、旧提交拒绝、缓存复用、场景版本切换和失败恢复。
- `scene_preview_gui_test <正式应用> <已解析模型路径的 PMM>`：清除捕获环境，确认启动默认关闭，每个后端通过实际菜单和关闭按钮运行三轮。
- `run_cpu_geometry_diagnostic.py --preview-ui`：真实 PMM v1/v2 编辑、播放、Save As、回读；每个后端三轮打开关闭；同一应用进程卸载 v1、验证空场景提示、通过文件框重载 v2；严格检查关闭后的资源与设备归零。

图形结论限定本机 GPU 和上述场景范围。详细结果与二进制哈希记录在 `exports/preview-controller-acceptance.json`；macOS 仍需 CI 实测。

## 2026-10-14 验收状态

恢复后，当前 x86/x64 二进制各完成一轮新审计和一轮匹配审计的直接 CPU 模式验收，四轮均为 `PASS`。每轮覆盖 PMM v1 的五个、保存回读后 v2 的四个实时检查点；1145 条逐绘制图像/离屏生命周期记录和 559 次 CPU 字段/字节对照全部一致。图像验收覆盖地面线、地面面片、饰品、投影阴影、模型材质和描边，两个预览后端均通过实际缩放、最小化恢复、设备替换及重复打开关闭。

| --- | --- | --- |

直接模式没有生成 `cpu_inputs.*.csv`，普通几何发布没有原生比较；九个受控原生验收检查点仍保留字段与图像证据。每轮所有 22 条关闭记录均确认驻留资源、退休资源、设备身份和 epoch 归零。同进程 v1 卸载、空场景提示和 v2 重载也通过。原始 PMM 哈希保持不变。上述资源指标是可追踪缓存，不能作为进程或驱动总内存的度量，呈现次数随运行时序变化。

这些零差异结果限定本机 TITAN Xp、单采样 PMD、MME 效果关闭、空背景屏幕来源，并显式选择 DX9 Mip 准备及 `diagnosticAlpha12`、`diagnosticTextureFma`、`diagnosticSpecularFma`。产品默认 BoxLinear 和关闭数学兼容开关的可用性另行验证，不承诺该默认配置与 DX9 像素一致。汇总 `exports/preview-controller-acceptance.json` 已更新为 `PASS`，记录当前应用、GUI 与关键源码哈希及历史失败尝试。预览仍默认关闭，主窗口继续使用 DX9；MSAA、MME、PMX、其他 GPU 和 macOS 实测仍待后续验收。

共用控制器在 x64/x86 各通过四项硬件/WARP CTest；Linux 可移植资源测试 13/13 通过，证据检查的六项负例测试通过。正式 x64 构建关闭诊断、关闭 DX9 RHI 适配器，在没有捕获环境时通过真实 PMM 菜单测试：启动默认关闭，DX11/DX12 各三轮打开、绘制和关闭。正式资源准备使用 BoxLinear；这项可用性测试不代表 DX9 图像零差异。

另以独立构建同时关闭诊断、预览和 DX9/DX11/DX12 RHI 适配器，x64 主应用完整编译、链接通过，确认可选择原有 DX9 应用构建。

本日较早的 x86 首轮审计完成 v1 五个检查点及 v2 首个检查点，748 条图像/离屏生命周期记录与 365 次 CPU 字段/字节对照一致，同进程 v1 卸载、空场景提示和 v2 重载通过。但随后关闭窗口的异步测试过早检查窗口数量，整轮结果为 `FAIL`。测试已改为同时等待释放记录与窗口消失，保留了失败证据。

恢复前的 x86/x64 完整复验被主 DX9 设备创建失败阻断，实际 HRESULT 为 `0x8876086C/0x8876086A`。当时没有将旧审计用于授权新二进制的直接模式。独立探针的十二组参数及 `WM_CREATE` 创建设备均成功，输入桌面为 `Default`，同二进制改名启动仍失败；原始启动失败的原因尚未确定，不能仅归因于 RDP 或驱动配置。

恢复后的测试还修正了三处证据问题：窗口缩放改用桌面内两个明确不同的尺寸，避免系统尺寸限制及无变化恢复时错误等待重建；同进程 v1 卸载/v2 重载完成后，释放第一应用再启动独立 v2 检查进程，并记录启动退出码和错误框；材质诊断日志使用进程内唯一的提交编号，避免场景重载后编号归零、报告合并两个独立提交。完整门禁保持不变，失败尝试保留在汇总中。
